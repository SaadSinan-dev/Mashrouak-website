# Projects and Results loading: investigation and recovery

## Confirmed causes and live evidence

Investigated November 21, 2026. Read-only probes used the deployed public application at `https://mashrouak-net.pages.dev` and the configured Portfolio endpoint. `https://mashrouak.net` did not resolve in the test browser; this is an observation from this environment, not a diagnosis of the visitor's DNS. No production records, environment variables, rules, DNS or deployment configuration were changed.

## Request ownership and recovery

- `read-recovery.ts` owns error classification, abortable backoff and the shared 150ms lifecycle debounce. GET reads make at most three attempts per recovery burst, with exponential jitter and server `Retry-After` as the lower bound. Invalid payloads, permission failures and ordinary permanent 4xx responses do not retry. An explicitly reported publication-not-ready conflict is a bounded retryable consistency condition.
- Network events are hints, not proof of reachability. Actual HTTP responses determine success. Focus, online, pageshow, visible, resume and supported connection-change events coalesce. Hidden, offline, freeze and pagehide pause owned synchronization. No application timeout is imposed on long-lived realtime connections. Public content reads have a 15-second deadline; existing Portfolio HTTP reads retain their 30-second deadline, and revision checks retain eight seconds.
- `content-sync.ts` maintains one publication stream. Healthy SSE has a 60-second revision watchdog; unavailable SSE uses a 15-second conditional revision check. A failed revision burst opens the circuit until a recovery event. EventSource automatic error reconnection is closed and replaced by at most three controlled connection attempts; a server-closed/unsupported stream falls back to revision checks. Preview uses its existing separate resource and never enters the public cache.
- `portfolio-store.ts` shares one subscription/read between homepage, project grid, detail and Results consumers. A 250ms final-unsubscribe grace avoids churn during Strict Mode and short route transitions, then cancels requests, timers and listeners. Cached SDK snapshots cannot overwrite an already accepted public record; a late HTTP response cannot replace a newer authoritative live snapshot. Permanent Firestore errors stop automatic resubscription for that page lifetime. Terminal transient listener errors receive bounded reconnect attempts; ordinary transient transport retry remains the Firebase SDK's responsibility.
- Both resources preserve their last valid content. The existing Portfolio cache key and validated version-1 format remain compatible. Public CMS content additionally persists by API origin in `mashrouak-public:v1:*`; preview/private responses are never stored there. Fresh data clears failure indicators. Background revalidation does not display a new full-page loading screen. Exhausted HTTP bursts retain data and wait for a real lifecycle/recovery event or explicit Retry, rather than continuing a failing loop.
- The external function currently permits up to 60 seconds of fresh edge caching and up to 300 seconds of stale-while-revalidate. A JSON-only fallback can therefore lag a Portfolio publication under the provider's cache policy. This application cannot change that external server policy. Immediate updates continue to use authorized Firestore subscriptions when the external owner restores access.

## Verification

Run `npm test`, `npm run typecheck:all`, `npm run lint`, `npm run build:all` and `npm run test:sync:browser`. The synchronization browser suite uses real Chromium, the actual React application and controlled responses for fault injection; it records requests and status codes in `artifacts/sync-qa/browser-results.json`. It deliberately interrupts Firestore transport without suppressing SDK diagnostics. Unit tests drive subscription callbacks to distinguish permanent permission/query rejection from transient interruption, and verify stale callbacks, bounded retries, suspension and cleanup. Existing CMS publication and Results browser suites use isolated **local** PostgreSQL schemas, never the production database.

Screenshots for visual inspection are `revalidating-desktop.png`, `results-cached-en.png` and `results-cached-ar.png` under `artifacts/sync-qa/`. They contain isolated QA data. `live-portfolio-results.png` additionally shows the actual 13-project integration rendering locally while the local CMS backend is unavailable. Live credentials and configuration are not required to reproduce the fault-injection suite.

The lifecycle suite injects `freeze`/`resume` and visibility signals into the actual browser application. Chromium's protocol freeze/active command did not emit document lifecycle events for the visible headless tab, so that command is not counted as an OS-level suspension test. Actual Chromium offline/online simulation and an interrupted in-flight response are tested separately. Historical device suspension and the original incident's 400 bodies remain outside the captured evidence.
